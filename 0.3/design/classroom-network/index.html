Classroom network

Classroom network

How students' browsers reach each other's containers through a relay — on the teacher's laptop or on the internet — that is also a firewall, with rules modelled on OpenStack Neutron security groups, a gRPC control API, OpenID Connect sign-in and a high-availability plan.

You are reading the documentation of an outdated version, whose text may no longer be accurate. Go to the latest version.
Status: M-relay-1 and M-relay-2 shipped in relay v0.1.0, M-relay-2b (the live flow map) in v0.2.0 (see Relay); the rest is planned. The implementation lives in go-wasmcontainers/relay. This page decides what is built and records why, so the code can be reviewed against it. Milestones are named M-relay-1 and up.

The problem

A teacher has a laptop on the classroom LAN, possibly with no internet access. Ten to forty students each open the playground in their own browser (Chrome, Firefox or Safari, sometimes on a school-managed machine). Each browser runs WASI containers in Web Workers. Inside one browser, containers already share a virtual network. The lab now needs student A’s container to reach student B’s container, for example a web server on one side and curl on the other, and the teacher needs to decide and show which flows are allowed, the way a cloud’s security groups do.

The answer on this page: every browser opens one secure WebSocket to a relay that runs on the teacher’s laptop. The relay brokers socket-level (L4) flows between containers, and it is also a firewall: every flow is checked against security groups whose model is OpenStack Neutron’s. The teacher manages them through a gRPC control API. The brief called it the “c-api”; this page reads that as control API (the control plane, as opposed to the data plane that carries the containers’ bytes).

Traffic between two containers of the same browser does not leave it; the engine checks it against the same rules (see Where rules are enforced). Traffic between different browsers always crosses the relay: a star, so the firewall sees every flow.

1. Transport between the browser and the relay

Three candidates were compared.

WebSocket (wss)WebTransportWebRTC data channels

serverCertificateHashes lets a page connect to a server whose certificate no CA signed, by giving the SHA-256 of the certificate. The W3C WebTransport Candidate Recommendation (30 July 2026) and MDN set the constraints:

  • the certificate must be X.509v3, its total validity period must not exceed two weeks, and the current time must be inside it;
  • the accepted key algorithms are implementation-defined but must include ECDSA P-256 (secp256r1) and must not include RSA;
  • the hash is sha-256, over the DER encoding of the leaf certificate;
  • the option only works on a dedicated connection (allowPooling: false).

The relay can meet these: it generates an ECDSA P-256 certificate valid for at most 13 days (a margin under 14) when a class starts, and hands its hash to students in the join link. A class that lasts longer gets a new certificate and a new link.

WebRTC is rejected. Its value is a direct peer-to-peer path; the firewall must see every flow, so the topology would be a star through the relay anyway, and WebRTC would only add ICE, DTLS and SCTP to a connection the relay terminates. It is also not established that it can be used from the Web Worker that runs the engine.

Decision. WebSocket is the first transport because it works in every target browser, in a worker, and through the simplest server code. It carries everything over one TCP connection, so one lost Wi-Fi frame stalls every flow of that browser (head-of-line blocking); WebTransport removes that and is the second transport (M-relay-4), selected per browser by feature detection, with the same framing on its streams.

2. Reaching a LAN host from a web page

A page that talks to the teacher’s laptop runs into four browser rules.

  1. Mixed content. An https page cannot open ws://; MDN classes any non-upgradable insecure request as blockable, and the Local Network Access draft states that WebSocket has no RequestInit, so ws:// URLs cannot use its mixed-content exemption either. The relay must speak wss, so it needs a certificate the browser accepts.
  2. Local Network Access (formerly Private Network Access). The WICG draft (7 August 2026) classifies addresses as loopback, local (RFC 1918, link-local, fc00::/7) and public; a request from a document to a less public address space needs the local-network permission, only from a secure context. The WebSocket handshake is a fetch, so it is covered; WebTransport inherits the rule through fetch. Chrome’s announcement says the permission prompt launches in Chrome 142, and in June 2025 it still listed WebSocket, WebTransport and WebRTC as not yet gated. The design assumes they are gated: a page on GitHub Pages (public) that opens a socket to 192.168.x.y (local) triggers the prompt, and a school’s enterprise policy may pre-deny it. A page served from the relay itself is in the local address space, so its connections back to the relay are not “less public” and need no permission.
  3. Cross-origin isolation. The executor uses SharedArrayBuffer, which MDN allows only in a secure context that is cross-origin isolated. On GitHub Pages, which cannot set response headers, the playground gets this from coi-serviceworker; a relay serving the page sets Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy itself.
  4. Certificate trust. A WebSocket has no certificate-error interstitial to click through: either the browser already trusts the certificate, or the connection fails.

Where the certificate comes from, in order of preference

  1. A publicly trusted certificate from ACME. A school-owned name (say class.example-school.fr) resolves to the relay’s address — a private LAN address is fine — and a public CA issues its certificate: no student installs anything. Caddy’s automatic-HTTPS documentation states the key point for a LAN-only relay: with the DNS challenge, “the server requesting a certificate does not need to be externally accessible”; it needs credentials for the DNS provider. The DNS-01 challenge (RFC 8555 §8.4) proves control of the name with a TXT record at _acme-challenge.<name> whose value is the base64url SHA-256 of the key authorization. The relay takes its certificate from go-authn/servercert, the fleet’s shared source of TLS server certificates: files reloaded on change, or ACME through autocert with External Account Binding. servercert answers tls-alpn-01 and http-01 only (“No dns-01”), which covers a relay on the internet; it also covers a LAN-only relay whose organisation has a GÉANT TCS / HARICA account with pre-validated domains, which issues “with no ACME challenge at all”. For every other LAN-only relay, DNS-01 is added to servercert (shared code, not a copy in the relay). An IP-address certificate is not an option for a LAN relay: Let’s Encrypt issues them (generally available since 15 January 2026, short-lived profile only, 160 hours), but servercert refuses IP names, and whether a public CA would validate a private LAN address was not established here; a name is the path.
  2. The relay’s internal CA, when no name or no internet at issuance is available. wctr-relay init creates a root (ECDSA P-256), name-constrained to the classroom’s names and addresses, which a school installs on managed machines by the same policy channel that installs any CA. mkcert’s README states the risk of any such CA: its key “gives complete power to intercept secure requests” from a machine that trusts it — hence the name constraints, a 0600 key that is never exported, and wctr-relay ca rotate. Caddy’s internal issuer is the same idea (a local CA it tries to add to the system trust store, which “isn’t guaranteed to work” without privileges), but it lives in Caddy’s PKI app, not in CertMagic (which has no internal issuer), so embedding it would mean embedding Caddy.
  3. WebTransport certificate hashes from the GitHub Pages page (deployment (a)): no trust needed, under the constraints of §1.

Caddy as a front is the documented alternative for a teacher who already runs it: wctr-relay serve --tls off --listen 127.0.0.1:8080 (the relay refuses --tls off on any non-loopback address) behind Caddy’s reverse_proxy, with Caddy’s own ACME or tls internal and caddy trust. The relay still checks Origin and Host itself. If on-demand TLS is used it “must be both enabled and restricted” (Caddy’s words), with an ask endpoint.

Secrets: a DNS provider’s API token, an EAB HMAC key and the CA key are read from files (0600, owned by the relay’s user), never from a command line, an environment variable or a URL.

Join-flow detection

The join link (printed and shown as a QR code by wctr-relay class create) carries, in its URL fragment (never sent to a server): the relay’s LAN URL, its GitHub Pages fallback, the join code, and the WebTransport certificate hash when there is one. The page:

  1. fetches https://<relay>/v1/info (a small public JSON document: version, relay id, TLS mode) with a 3 s timeout; if it answers, the certificate is trusted (public ACME or an installed internal CA) and the browser is sent to the playground served by the relay (deployment (b));
  2. otherwise, if the page is on GitHub Pages and the browser has WebTransport with serverCertificateHashes, it connects with the hash (deployment (a));
  3. otherwise it tells the student exactly what is missing (install the CA, accept the Local Network Access prompt, or use another browser), rather than failing silently.

Whether a page loaded after a certificate warning is still a secure context in each browser is not established by the references opened here; M-relay-3 measures it in the three browsers before any path relies on a click-through.

3. Network model: L4 flows, not L3 packets

The containers’ sockets use the WasmEdge socket extension in the module wasi_snapshot_preview1, as github.com/stealthrocket/net imports it: sock_open, sock_bind, sock_listen, sock_connect, sock_recv_from, sock_send_to, sock_getaddrinfo, sock_shutdown, plus sock_getsockopt, sock_setsockopt, sock_getlocaladdr and sock_getpeeraddr. Its socket types are SOCK_STREAM and SOCK_DGRAM only; there is no raw socket. The engine therefore sees a container connecting to 10.42.2.2:80, never a packet.

The alternative is what container2wasm does: an L3 network stack based on gVisor’s netstack (c2w-net, built on gvisor-tap-vsock) that carries Ethernet frames, forwarded over WebSocket in its delegate=ws://... mode.

L4 flows (chosen)L3 packets (gVisor netstack)

Decision: L4. Addressing is still IP-shaped, because the lab teaches it:

  • one network per class, default 10.42.0.0/16; student n gets 10.42.n.0/24, the teacher 10.42.0.0/24; the relay allocates every address (as Neutron allocates fixed_ips), the browser never chooses one;
  • DNS: <container>.<student>.class resolves to the container’s address, through sock_getaddrinfo, answered by the relay; a container’s bare name still resolves inside its own browser;
  • TCP: listen registers the address and port at the relay; connect is a request to the relay, which checks the rules and opens a stream to the listener’s browser, or refuses (the caller gets ECONNREFUSED, or a timeout if the teacher chose “drop” for teaching);
  • UDP: each sock_send_to is one datagram frame with a source and destination, at most 8 KiB; the relay checks it and forwards or drops it.

Ping. The ABI cannot send ICMP, so ping is taught through a small extension the engine provides later (M-relay-5): an import module wctr_net with one function, icmp_echo(addr, seq, payload), which the driver turns into an echo frame. The relay answers it on behalf of the destination port if its rules allow ICMP echo ingress (protocol: icmp, port_range_min: 8, type 8). A ping image built against it gives the expected pedagogy: allowed, the student sees replies; removed, the pings time out, and the flow log shows the drop.

4. Firewall model, mapped from Neutron

The Neutron API reference defines a security group rule by direction (ingress or egress), ethertype (IPv4 or IPv6), protocol (tcp, udp, icmp, …, or any), port_range_min and port_range_max (for ICMP: the ICMP type and code), and one of remote_ip_prefix, remote_group_id or remote_address_group_id. A security group has a stateful flag: a stateless group “bypasses connection tracking”, so both directions of a flow need rules. Nova’s guide states the overall policy: “Security groups deny everything by default, so rules indicate what is allowed”, and adding a rule is additive. A port carries security_groups, fixed_ips, port_security_enabled (“security group rules and anti-spoofing rules are applied”) and allowed_address_pairs. Neutron creates, for each project’s default group, four rules (all IPv4/IPv6 egress, and ingress from ports in the same group), and for other new groups only the two egress rules; a template of those rules is configurable (used_in_default_sg, used_in_non_default_sg, remote_group_id: PARENT). Quotas count security_group and security_group_rule per project.

A port is created when a container attaches to the class network and is deleted with it. Only the teacher can set port_security_enabled: false. There is no allowed_address_pairs: a container has exactly one address, which the relay assigned.

Policy and evaluation

  • Default deny. A flow is allowed only if a rule allows it.
  • Both ends. A flow from port S to port D is allowed iff S’s egress rules allow it and D’s ingress rules allow it, as Neutron filters at each port.
  • Order-free. Rules only allow, groups on a port are a union, so there is no order to get wrong: the result is the same whatever order rules were added in. The decision names the rule that allowed it, or “no rule” if none did.
  • Default groups. Each class gets a default group with Neutron’s four rules (egress allowed, ingress from the same group), and the teacher can switch the class template to isolated (egress only to the teacher’s subnet, no ingress), which is the better start for a lesson on opening ports.
  • remote_group_id matches the current addresses of every port in that group, so a rule “ingress tcp 5432 from group web” follows containers as students start and stop them.

Statefulness

Statefulness is connection tracking of L4 flows, which the relay has for free because it brokers every flow:

  • TCP (stateful group): the rules are checked once, at connect; the stream then carries both directions until either side closes.
  • UDP (stateful group): an allowed datagram creates a conntrack entry keyed by the 5-tuple; replies match it; it expires after 30 s without traffic.
  • Stateless group: for TCP, the reverse direction (D’s egress, S’s ingress) must be allowed too, or the connect is refused; for UDP, every datagram is checked both ways. This is Neutron’s “two rules for a TCP flow”, visible to students.
  • Rule changes: after any change, the relay re-evaluates open flows and resets the ones no longer allowed, logging them as revoked. A firewall that silently keeps old connections confuses a lesson.

Where rules are enforced

Between browsers, at the relay: it is authoritative. Inside one browser, the engine applies the same rules, pushed by the relay with the session, so that a lesson works the same with two containers of one student. That copy is advisory: a student who modifies their own page only affects their own containers, which they control anyway.

Flow logs

Every decision can be logged: time, class, source and destination session, port, address and port, protocol, verdict (allow, deny, revoked), the matching rule or no rule, and at close the bytes each way and duration. Rules carry a log flag; denies are always logged. The teacher streams logs live (CLI, dashboard); a student sees the decisions about their own ports, which is the point of the exercise (“why can’t I reach Bob’s server?”).

The live flow map

The relay serves a page that draws the class’s network as it happens: nodes are sessions (the students and the teacher) holding their containers, coloured by security group; edges are live flows, their width following throughput; denied flows flash red with the rule decision that refused them (“no ingress rule of bob/web allows tcp/80”), because seeing the refusal is the lesson.

  • Data. The page calls a server-streaming RPC, FlowLogService.WatchFlowMap, over the Connect protocol (the reason connect-go was chosen: “the other RPC types also support HTTP/1.1”, server streaming included, so a browser needs no proxy). The relay aggregates: every tick (default 4 Hz) it sends one update holding the per-edge counters (src port → dst port, protocol and port: bytes each way, flows opened, open, denied) and the discrete events since the last tick (opened, closed, denied, revoked, with the rule ids). A slow page gets coalesced updates — the newest state replaces the unsent one — never an unbounded queue. A view is capped (400 nodes, 2 000 edges; past that the update says what was left out).
  • View. A stable, incremental layout, not a force simulation (no full relayout per tick): sessions are boxes on a grid ordered by subnet (teacher first), containers inside them, so a node does not move when traffic changes and 40 students × several containers stay readable on a projector. Click a node or an edge for its details (groups, the rules that matched, conntrack state, counters). Filters by student, group and port. Light and dark themes. Pause and replay of the last minutes are deferred (the ring of the last 1 000 events is already kept).
  • Technique (decided 2026-10-26): the fleet’s own toolkit. The page is a Go js/wasm application built on go-widgets/toolkit and run in a <canvas> by go-widgets/webcanvas, which blits “an RGBA framebuffer into the canvas and routes DOM pointer and keyboard events back into the scene”. The widgets a flow map needs and the toolkit lacks — a node-link graph view with groups, animated edges and incremental layout, a legend, a filter bar, a detail panel, a sparkline — are added to go-widgets, generic and reusable, under its conventions (MVVM, Theme, keyboard navigation, its coverage gate), each in its own pull request and minor release; the relay imports them. Everything is served by the relay (same origin, the .wasm included), under a strict Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval' (the narrowest allowance WebAssembly compilation needs), no inline script, no third-party request — the relay runs without internet. The join QR code is drawn from go-gfx/qr’s module matrix. Because a canvas has no DOM to assert on, the page’s tests read the view model (MVVM’s testable layer), which the page exposes to the test harness.
  • Access. The teacher’s view of the whole class needs the admin role (the admin token on loopback or the Unix socket, or the OpenID Connect teacher role in internet mode). A student may open their own view: only the flows that touch their own containers, with the other end named but no flow between two other students — the privacy between students the class needs.
  • Tests. Playwright (Chromium and Firefox) drives real flows through an in-process relay and asserts what the page’s view model says (edges present, a denied flash with its rule, counters moving), not screenshots; the update latency from a flow to the screen, the frame time at about 200 nodes and 1 000 edges on one core, and the relay’s CPU at 40 sessions are measured.

Quotas

Per class, as Neutron’s: security_group (default 50), security_group_rule (default 500), and port (default 40 × 10). Per session, for safety rather than pedagogy: see the security audit.

5. Control API

Services

The control API is gRPC, described in one .proto; the relay serves it with connect-go, whose handlers support gRPC, gRPC-Web and the Connect protocol and mount on a plain net/http server. The Connect protocol uses no HTTP trailers and supports server streaming over HTTP/1.1 (bidirectional streaming needs HTTP/2), so a browser dashboard can call the same API, including the live flow log, without a proxy. Nothing in the API needs bidirectional streaming.

syntax = "proto3";
package wasmcontainers.relay.v1;

service ClassService {
  rpc CreateClass(CreateClassRequest) returns (Class);       // teacher
  rpc GetClass(GetClassRequest) returns (Class);
  rpc RotateJoinCode(RotateJoinCodeRequest) returns (Class); // teacher
  rpc Join(JoinRequest) returns (JoinResponse);              // student: code -> session token
  rpc ListSessions(ListSessionsRequest) returns (ListSessionsResponse);
  rpc KickSession(KickSessionRequest) returns (Empty);       // teacher
}

service NetworkService {
  rpc GetNetwork(GetNetworkRequest) returns (Network);
  rpc ListPorts(ListPortsRequest) returns (ListPortsResponse); // student: own ports only
  rpc UpdatePort(UpdatePortRequest) returns (Port);            // security_groups, port_security_enabled
}

service SecurityGroupService {
  rpc ListSecurityGroups(ListSecurityGroupsRequest) returns (ListSecurityGroupsResponse);
  rpc CreateSecurityGroup(CreateSecurityGroupRequest) returns (SecurityGroup);
  rpc UpdateSecurityGroup(UpdateSecurityGroupRequest) returns (SecurityGroup);
  rpc DeleteSecurityGroup(DeleteSecurityGroupRequest) returns (Empty);
  rpc CreateRule(CreateRuleRequest) returns (SecurityGroupRule);
  rpc DeleteRule(DeleteRuleRequest) returns (Empty);
  rpc ListDefaultRules(ListDefaultRulesRequest) returns (ListDefaultRulesResponse);
  // Dry run: which rule, if any, would allow this flow, and at which end.
  rpc ExplainFlow(ExplainFlowRequest) returns (FlowDecision);
}

service FlowLogService {
  rpc WatchFlows(WatchFlowsRequest) returns (stream FlowEvent); // server streaming
}

message SecurityGroupRule {
  string id = 1;
  string security_group_id = 2;
  Direction direction = 3;            // INGRESS, EGRESS

The data plane is not gRPC: it is the binary framing on the WebSocket (below), because it carries every byte the containers exchange and its cost per frame matters.

  • The admin token is 256 random bits generated by wctr-relay init, stored 0600 under os.UserConfigDir(), compared in constant time, never printed except by an explicit wctr-relay token show, never in a URL.
  • The class code (10 characters, from an alphabet without look-alikes) is shown on the teacher’s screen and in a QR code. Join exchanges it with a display name for a session token: signed by the relay (Ed25519), bound to the class and the session id, valid 12 hours, revoked by KickSession or by rotating the code.
  • mTLS is not used for students: provisioning client certificates into 40 browsers is the problem the class code solves. A teacher may require mTLS on --admin-listen.
  • Authorization is checked in the handler from the token’s claims, never from a field of the request (a student cannot pass another session’s id).

Data plane framing

One WebSocket per browser, binary messages, one frame per message:

 0      1      2              6              10
 +------+------+--------------+--------------+----------------+
 | type | flags| stream id    | length       | payload ...    |
 | u8   | u8   | u32 BE       | u32 BE       | <= 16 KiB      |
 +------+------+--------------+--------------+----------------+

Frame types (version 1, numbered in the protocol): HELLO, WELCOME, ATTACH, ATTACHED, DETACH, LISTEN, LISTENING, UNLISTEN, CONNECT, ACCEPT, REFUSE, DATA, WINDOW, CLOSE, RESET, DATAGRAM, RESOLVE, RESOLVED, RESULT, REAUTH, GOAWAY; ECHO comes with ICMP in M-relay-5. The client allocates odd stream ids and the relay even ones. The session token is checked before the WebSocket upgrade: a browser cannot set an Authorization header on a WebSocket, so the token travels as a second subprotocol (Sec-WebSocket-Protocol: wctr-relay.v1, bearer.<token>) — a header, never a URL. REAUTH hands the relay a fresh token on the open connection. Control payloads are protobuf messages from the same .proto; DATA payloads are raw bytes. Flow control is credit-based per stream (64 KiB initial window, WINDOW frames return credit) and per connection (1 MiB), so one fast sender cannot fill the relay’s memory for a slow reader. The relay rewrites every source address: a frame names a stream or a port the session owns, never an address the browser chose.

Internet mode: OpenID Connect

The same star can run on a server on the internet, for remote or hybrid classes. It must then not be open to everyone, so it signs people in with OpenID Connect, using the fleet’s own libraries:

PieceLibraryWhat it does here
verifying tokensgo-authn/oidcthe relay verifies the token that comes with Join, RefreshSession and the teacher’s calls: issuer compared exactly, audience required, expiry required, an allowlist of signature algorithms (no none, no HMAC), key-set refetches bounded. With Type: "at+jwt" it refuses an ID token presented as an access token (RFC 9068 §4, which the library cites).
logging people ingo-authn/rpthe browser login (authorization code with PKCE S256, state and nonce) and the teacher’s wctr-relay login, a loopback login (RFC 8252) that listens on 127.0.0.1 only and opens the system browser
universitiesgo-authn/bridgean OpenID provider in front of a SAML federation: people “log in at their own university, through RENATER’s Fédération Éducation-Recherche or eduGAIN”. The recommended identity provider for academia, since many university IdPs speak SAML only.

Authorization model.

  • Issuer and audience pinned in the relay’s configuration (--oidc-issuer, --oidc-audience); one issuer per relay.
  • Class membership: an identity alone admits nobody. A student still joins a class with its join code; the class may also list who may join — sub:<subject>, email:<address> (only an address the issuer marked verified: go-authn/oidc’s Username falls back to email only when email_verified is true, for the same reason) or group:<group> — and may require an identity (--require-identity), which a relay on the internet sets on every class.
  • Teacher role: a configured group claim (--teacher-group) gives the admin role, but only on the admin listener, never on the public one.
  • One identity, one session per class: joining again returns the same session (same addresses), and the per-session quotas are therefore per identity, not per IP address — a class behind one NAT is not one student.

Long connections and short tokens. A data connection lasts a lesson; an access token lasts minutes. The relay’s own session token is what the data connection holds, bound to the session; before it expires the page calls RefreshSession (with a fresh OIDC token, from the refresh grant go-authn/rp handles) and sends the new session token in a REAUTH frame. No flow is dropped. A connection whose token expires without REAUTH gets GOAWAY and closes. Logout and revocation: the teacher’s KickSession, or deleting the class, ends the session and its tokens at once (the relay checks that the session exists on every authentication, not only the signature).

Internet hardening.

  • Authenticate before upgrading: the session token is checked before the WebSocket upgrade, and before any per-session state is allocated; an unauthenticated request costs a header parse and a signature check.
  • Per-IP limits before authentication: token buckets on Join and on upgrade attempts per source address, and a cap on concurrent unauthenticated handshakes. ReadHeaderTimeout (5 s), MaxHeaderBytes (16 KiB) and idle timeouts against slowloris.
  • Max sessions per identity (one per class) and per class (its subnets).
  • Frame and flow bounds as on the LAN (security audit).
  • No admin API on the public listener: the admin API stays on the Unix socket and loopback, or on a separate --admin-listen that requires the teacher role (or the admin token).
  • Audit log (JSON lines, 0600): logins, refusals, kicks, class and rule changes, with pseudonymous identities.

Privacy (GDPR). Students are data subjects, often minors. The relay stores, per session: a display name the student typed, a derived DNS label, and — with OpenID Connect — a pseudonymous identifier (a hash of issuer and subject), never the token, the e-mail address or the groups (they are checked at the moment of joining and dropped). Flow logs hold addresses and ports, not contents. Retention: everything about a class is deleted with the class (wctr-relay class delete); the audit log is pruned after 30 days by default (--audit-retention). The teacher’s institution is the controller and should say so in the course’s information notice.

Chaos cases

A student reloads the pageThe page reconnects with its session token; within a 120 s grace period the relay keeps the session’s ports and addresses; open streams are reset (the container sees a connection reset, as after a network cut); listeners are re-registered by the engine.

7. Performance

Budget. The relay must not be what limits a lab. The assumptions to measure, not results:

  • 40 students on one access point share its airtime; a lab’s traffic is small (HTTP requests, a database query, a chat), a few hundred kB/s per student, so the aggregate stays far below what one Go process forwards;
  • container-to-container round trip ≈ two Wi-Fi round trips (A to relay, relay to B) plus the relay’s processing, which must stay under 1 ms at the 99th percentile;
  • framing cost: our 10-byte header, the WebSocket header (2 to 10 bytes, plus a 4-byte masking key from client to server, RFC 6455) and the TLS record: under 0.3 % for a full 16 KiB frame, significant only for very small writes, which the engine coalesces within one event-loop turn;
  • head-of-line blocking on the single TCP connection is the main latency risk on a lossy Wi-Fi; WebTransport’s independent streams are the remedy.

High availability

The problem. A class runs on relays in a datacenter; if that relay stops answering, the class must move to another one without losing its setup.

What state exists.

PlaneStateOn failover
controlclasses, join codes, members and their identities’ hashes, security groups and rules, port and address/DNS assignments, session-token signing keys, audit logreplicated: survives
datalive streams, UDP connection tracking, listenersnot replicated: flows are reset (containers see ECONNRESET, which is teachable); listeners are re-registered by the engines when they reconnect; addresses, names and rules are the same

Replication: Raft, not a CRDT. The control plane is a replicated state machine (the Raft paper, §2: servers “compute identical copies of the same state” and are “fully functional (available) as long as any majority of the servers are operational”; “they do not depend on timing to ensure the consistency of the logs”). Security rules need that linearizability. A CRDT (go-crdt exists in the fleet) merges concurrent updates instead of ordering them: an add-wins set would bring back an allow-rule the teacher deleted on another replica during a partition. A deleted allow-rule must never reappear by merge, so CRDTs are the wrong tool here. The library candidate is etcd’s raft (the core algorithm only: “the application supplies its own network transport and persistent storage”; Apache-2.0; used by etcd, CockroachDB and TiDB). The relay already reaches its state through a Store interface (FileStore on a single relay), which the replicated store implements.

One relay per class: an epoch lease. The star needs a class to live on one relay at a time. The replicated store holds, per class, a lease (relay_id, epoch, expiry); a relay takes or renews it through the log, and each new holder increments the epoch (Raft’s terms are the model: “terms act as a logical clock”, and a server rejects a request with a stale term). The epoch is in Welcome and in Class; a client refuses a relay that shows an older epoch than one it has seen (fencing), so a partitioned old holder cannot keep half a class. A relay that cannot renew its lease stops serving the class before the lease expires, with a margin for clock drift.

Quorum. A majority quorum of 2 datacenters does not survive the loss of either (2 of 2 needed). Three sites are needed: two datacenters and a small witness (a third voter that serves no class). The trade-off is written down rather than hidden: without the witness, a two-site deployment is active/passive with manual failover.

Client-side failover, after DERP. Tailscale’s DERP documentation describes the pattern: each client gets a map of relays, picks one by latency, “selects the next closest region” when its region is unreachable, and saves the list so it works while the coordination server is down. Ours: the join link carries a signed class descriptor listing the relays in order (not DNS-only failover: resolvers cache past a TTL). A client health-checks, reconnects with exponential backoff and jitter, and resumes with its session token, valid on any relay of the cluster (signing keys are in the replicated store and rotated through it; OpenID Connect tokens stay valid because issuer and audience are the cluster’s). Each relay has its own certificate from servercert.

Phase 2: federation. Relay-to-relay links would let one class span relays (geographic proximity, partial failure), the firewall still enforced at both ends. Not before the single-holder design is shipped and measured.

Chaos plan (M-relay-HA): kill the lease holder in the middle of a lab; partition one datacenter; skew the clocks of the lease holder; run mixed relay versions during a rolling upgrade; make every student reconnect at once (thundering herd: jitter, and admission control that answers “retry after” rather than accepting more than it can serve).

What decided it.

  • With end-to-end WireGuard, the relay sees nothing: good for privacy, but there is no relay-side enforcement and no relay-side flow log. Filtering at the receiver is sound against untrusted students (a student can only weaken their own node), but egress rules cannot be enforced on a node the student controls, and logs kept by the endpoints can be forged by the student whose flows they describe. The relay-side log is the lesson.
  • Neutron’s model only partly translates to Tailscale ACLs: ingress rules map to tags and ports; egress rules and stateless groups do not.
  • headscale has no HA, so adopting it would not remove the Raft work.
  • A 26 MB WireGuard + netstack per tab, against a socket-level relay that adds no network stack to the engine (performance of both is unmeasured).

Decision: hybrid (option C). Our relay stays the classroom data plane and firewall; identity and certificates come from go-authn; client failover follows DERP’s ordered-relay pattern. A later option, not planned: tsnet in the teacher’s relay to reach native machines on an existing tailnet.

8. Roadmap and what the engine must expose

The engine’s NetworkDriver

The engine maps the socket host functions onto a driver; the in-browser network it has today becomes the local driver, and the relay is a second one:

// Package netdriver, in go-wasmcontainers/engine (planned).
type NetworkDriver interface {
	// Attach gives a container an endpoint on a network; the driver
	// assigns its address and DNS name.
	Attach(ctx context.Context, c ContainerRef, network string) (Endpoint, error)
	Close() error
}

type Endpoint interface {
	Addr() netip.Addr
	Listen(ctx context.Context, network string, port uint16) (net.Listener, error)       // "tcp"
	Dial(ctx context.Context, network string, addr netip.AddrPort) (net.Conn, error)      // "tcp", "udp"
	ListenPacket(ctx context.Context, network string, port uint16) (net.PacketConn, error) // "udp"
	Resolve(ctx context.Context, name string) ([]netip.Addr, error)
	Detach() error
}

The engine owns this interface; the relay’s client library implements it, so native engines (wazero) and browser engines use the same driver code, and the relay’s tests need no browser.
